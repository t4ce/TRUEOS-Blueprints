XERJ persistent native launcher

Build from the TRUEOS-Blueprints repository:
    cargo bp probes/xerj_service

Full engine and crypto-enabled probe builds also require GNU binutils with
ld.bfd or GNU ld. The SDK materializes retained ELF COMMON storage before
checking and packaging the native module.

Install xerj.bp and xerj-service.bp through the regular AppDB workflow. Launch
the exact bare app name in Shell3:
    xerj-service

The launcher stays alive and owns one full XERJ engine child. It sets the
working directory to /apps/xerj, stores engine data in /apps/xerj/data, binds
127.0.0.1:9200, and disables feedback with both --disable-feedback and
XERJ_DISABLE_FEEDBACK=true. XERJ creates its usual REST and gRPC listeners on
9201 and 9202. Authentication and the engine's feature defaults are preserved.
The launcher forwards the child's stdout bytes and flushes them unchanged.
It does not claim readiness or successful indexing from lifecycle status;
check the engine's readiness/API responses through its normal clients.

`xerj mcp --ensure-local` starts this installed Blueprint headlessly when the
authenticated node is absent, before accepting MCP requests. The packaged
Codex default instead uses `xerj mcp --lazy-local`: initialize, tools/list and
ping need only the MCP helper Hull; the first node-backed tool starts or reuses
this service and waits for authenticated readiness. The launcher and its engine
therefore occupy no Hulls before that first use when the service is stopped.
The first tool call has a 90-second activation deadline in addition to its normal
node request deadline; Codex supplies a 150-second tool timeout.

This launch is independent of the MCP client; closing one Codex session does
not stop the engine used by other clients. The service remains running after
first use. It does not automatically index the editor workspace or start a
filesystem watcher. Folder indexing and `autoindex --watch` are separate jobs;
an EDIT integration can request them when that workspace needs them.
For continuous database ingestion, explicitly launch xerj-service so configured
live sources can resume before any MCP tool is used.
Appbundle installation supplies xerj-service.bp and xerj.bp before that call,
so it uses AppDB directly and performs no runtime catalog download.

The launcher retains an exclusive /apps/xerj-service/service.lock before spawning its
engine. A competing launcher exits without another child. `replicatable=false`
is checkpoint metadata, not singleton admission. The engine also retains its
own data-directory lock and --no-auto-port fixes the expected endpoint.
Stop the parent xerj-service Hull to stop its owned
engine child; dropping the launcher also requests child termination. Native
parent/child Hull ownership handles cleanup when the parent is terminated.
Do not run another engine on the same data directory or normal ports.

Launch, output draining, lifecycle polling and cleanup stay on the original
Hull entry thread. Unexpected child exit is an error. There are no subprocess
or network stand-ins on the host: running the host executable returns an
explicit unsupported-platform error. No field reports are sent.
