How the simulation works — and its limits
GPU state → integrate → sort cell IDs → cell ranges → count contacts → solve contacts → next GPU state

Screen-down mode converts camera-down into a world-space gravity vector before each physics tick. Dragging changes that acceleration, not the stored positions or velocities; a settled pile can move again without resetting. Paused scenes stay paused. This is interactive gravity, not a moving-wall model with angular momentum, rolling, or rotational inertial forces.

Physics runs in GLSL ES 3.00 vertex shaders using transform feedback. Integer-texture shader passes build a uniform spatial grid. Each sphere gathers neighbors from its own cell and 26 adjacent cells. Complete cell ranges are used: there is no hidden fixed-size bucket or neighbor-count truncation.

The grid is rebuilt every substep. A correction halo lets contact iterations reuse that grid safely while each projection is bounded. Every invocation writes only its own sphere; all neighbors are read from a stable snapshot. Sorting is O(N log²N) here; crowded cells can still make local contact work quadratic.

This is an approximate, discrete many-body contact solver, not the earlier isolated-pair exact time-of-impact solution. Adaptive substeps limit free-flight travel to 0.4 of the smallest radius per substep. Gravity uses at least four substeps. They reduce tunneling; they are not a guarantee for every 3D grazing collision. No spin, rolling resistance, exact static-friction solver, sleeping, or continuous sphere–sphere collision detection is implemented.

Wall handling computes the first exit during a constant-velocity segment, then projects the final center inside radius 100 − sphere radius. Contact projections keep spheres contained, but dense piles can retain small overlaps. Restitution is disabled below a normal approach speed of 1 unit/s to reduce resting jitter. Numerical projection, penetration-bias impulses, multiple-contact weighting, and the hard speed limit mean total energy is not guaranteed conserved, even at bounciness 1.

Positions and velocities never go through a JavaScript simulation loop. JavaScript only seeds/reset states, dispatches GPU work, updates the UI/camera, and optionally reads diagnostics. On a software graphics backend, the graphics driver itself executes shader work on the CPU.
